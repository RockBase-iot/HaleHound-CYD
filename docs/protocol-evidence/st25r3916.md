# ST25R3916 Evidence Gate

Status: `RESERVED — NOT IMPLEMENTED`

Scope: `St25r3916Transport`（预留传输实现）、`st25r3916BringUpSteps()`（上电计划表）、
`st25r3916SiliconCaps()`（硅片能力，与驱动能力分开）。

> **本文件刻意是「计划」而不是「证据表」。** 与 `mifare-classic.md` / `pn532.md` 不同，
> 这里没有可复算的逐位演算，因为**寄存器级驱动尚未编写**，也就没有任何实现细节取得了
> 证据等级。写下来的目的是：① 让「为什么现在不做」有据可查；② 让将来接管的人有一份
> 有序的开工清单，而不是从芯片手册第 1 页重新推。

## 0. 决策：为什么现在只预留接口

BOSS 的指令是「ST25R3916 相关实现可以进预留接口」。本仓库按这条执行，理由是**当前硬件
上装的是 PN532（NM-RF-HAT，I2C）**，ST25R3916 不是这块板上的在读卡器：

- 立即写一份无法上机验证的寄存器驱动，产出的是**未验证代码**，而本仓库的口径是
  `Model Verified` / `Build Verified` / `Hardware Verified` 三级分开，不把前两级说成第三级。
- 反之，**协议层必须现在就跟传输层解耦**，否则将来接第二个后端时要回头重写
  `Iso14443aFraming` / `MifareClassicDriver` / `IsoDepSession`。所以正确的动作是：
  先把 `IRfidTransport` 抽出来，再声明一个「不假装能工作」的第二实现。

因此 `St25r3916Transport` 的每一处行为都是为了这个目的：

| 成员 | 行为 | 为什么这样 |
|---|---|---|
| `begin()` | **恒返回 `false`** | 返回 `true` 而背后没有驱动，会让 feature 启动后在使用时才失败 |
| `ready()` | 恒 `false` | 同上 |
| `caps()` | **全 `false`** | 驱动缺位时这是唯一诚实的答案；能力矩阵据此置灰屏幕 |
| `available()` | 恒 `false` | 调用方用它决定「要不要在主菜单里出现这个后端」，与 `caps()` 分开 |
| `unavailableReason()` | 返回具名原因 | 供选择器显示详情行，而不是笼统的「不支持」 |
| 其余方法 | `RfidStatus::Unsupported` | |

**`caps()` 与 `st25r3916SiliconCaps()` 是两个数，不是笔误。** 前者描述**驱动**（全否），
后者描述**硅片**（一旦驱动落地能拿到什么）。分开是为了让选择器能显示「本驱动不支持
iCLASS」与「硅片支持 iCLASS」两件不同的事，避免一个数字同时冒充两者。

### 0.1 硅片能力（`st25r3916SiliconCaps()`）

| 能力 | 值 | 备注 |
|---|---|---|
| ISO14443-A | ✔ | |
| ISO14443-B | ✔ | PN532 硅片支持但本驱动不构帧；这里是硅片级 |
| ISO15693 | ✔ | |
| ISO-DEP | ✔ | |
| MIFARE Classic | ✔ | |
| MIFARE Ultralight / NTAG | ✔ | |
| **iCLASS** | **✔** | **PN532 硅片做不到，这是当前板唯一够不到的能力** |
| 裸收发 | ✔ | |
| **硅片内防冲突** | **✘** | **没有状态机可委托** —— ISO14443-3 全部是主机代码 |
| 仿真 | ✔ | |
| 125 kHz | ✘ | 13.56 MHz 器件 |
| **mfkey32 nonce 捕获** | **✔** | **PN532 从不交出 Crypto1 nonce** |

`siliconAnticollision = false` 是本后端与 PN532 的**结构性差别**，也是 `IRfidTransport`
把「激活」与「收发」拆开的直接原因：PN532 上一个 `InListPassiveTarget` 就完成了整个
ISO14443-3，主机一个 REQA 字节都不用发；ST25R3916 必须主机逐帧驱动。上层通过
`caps().siliconAnticollision` 选择走哪条路，两个后端都不向上泄漏自己的形状。

## 1. 上电计划（`st25r3916BringUpSteps()`）

有序，且每步都标注它**解锁哪项能力** —— 这样 UI 能说出「iCLASS 被第 9 步卡住」，
而不是笼统的「不支持」。全部 `done = false`。

| # | 步骤 | 内容 | 解锁 |
|---|---|---|---|
| 1 | SPI 寄存器访问 | 写 mode-definition 与 IO-configuration 寄存器，再读**已知寄存器**（IC identity `0x3F`）回来，以证明总线与片选 | 后端能否出现 |
| 2 | 直接命令通道 | 直接命令（Set Default / Analog Preset / Calibrate / Adjust Regulators）与振荡器稳定等待，之后才能做场操作 | 场控制 |
| 3 | 中断路由 | RXE / TXE / 冲突 / FIFO 水位的 IRQ 掩码，用**有界等待**挂在 IRQ 脚上，而不是轮询寄存器 | 其后所有时序敏感步骤 |
| 4 | 场开关 | 稳压器与驱动器配置，经 auxiliary / driver 寄存器做 `fieldOn` / `fieldOff`，含基于 DAC 的功率爬坡 | ISO14443 激活 |
| 5 | ISO14443-A 软件成帧 | REQA/WUPA、防冲突、SELECT 由 `Iso14443aFraming` 构造后经 FIFO 打出。**此件无激活状态机，整个 ISO14443-3 是主机代码** —— 这正是成帧层从一开始就写成传输无关的原因 | 卡激活 |
| 6 | CRC 与奇偶配置 | 收发两侧的硬件 CRC-A，以及 REQA/WUPA 的 4 位短帧处理（它们**不带 CRC**） | 卡激活 |
| 7 | 带超时的收发 | FIFO 装载 → 发送 → 挂 IRQ 等**真超时** → FIFO 取空 → 把 CIU 错误标志映射到 `RfidStatus` | MIFARE Classic / NTAG / ISO-DEP |
| 8 | Crypto1 nonce 暴露 | 交回 nested / hardnested 所需的 (nonce, response) 对 —— PN532 永不交出 | 嵌套攻击，以及诚实的 mfkey32 捕获 |
| 9 | iCLASS 模式 | ISO15693 风格的 13.56 MHz 成帧 @52 kbps，加上 3DES 块交换，使凭据能在板上解密 | iCLASS / HID 凭据读取 |
| 10 | 卡仿真 | 目标模式，使读卡器能**出示**一张凭据而不只是读 | HF 仿真 |

### 1.1 为什么是这个顺序

- 第 1 步就能定生死：`0x3F` 读不回来，后面九步都不必写。**先做可证伪的一步。**
- 第 3 步排在第 4 步之前，因为场开关与后续每一步都要等 IRQ；没有 IRQ 就只能轮询，
  而轮询在 ISO14443 的 μs 级窗口里来不及。
- 第 5、6 步放在「场」之后、「收发」之前，因为纯主机的成帧/CRC 可以用 `test/native`
  在**没有硬件**的情况下验证，而这一步的产出（帧）正是第 7 步的输入。
- 第 8 步独立于第 9 步：nonce 捕获只服务于 MIFARE Classic，iCLASS 不依赖它。
- 第 9 步是本后端存在的**唯一不可替代理由**（PN532 做不到）；若只想先要一个「更快的
  读卡器」，第 1–7 步就够了。

## 3. 与现有代码的接缝

已经就位、**不需要**因 ST25R3916 而改动的东西：

- `IRfidTransport` —— 两个后端的共同接口；`siliconAnticollision` 是分流开关。
- `Iso14443aFraming` —— 纯逻辑，无传输依赖。ST25R3916 用它**构造**帧（PN532 不用，
  因为硅片自己做）。§5 的级联几何与 CRC_A 对它同样成立。
- `MifareClassicDriver` —— 只依赖 `IRfidTransport`，认证/转储/写入的判定逻辑与后端无关。
- 裸收发路径送出的是 `buildAuthenticate()` 的**规范 8 字节**形式：那条「追加 UID」的
  quirk 被关在 `Pn532Transport` 内，不会传染到这个后端。

需要新增的：`St25r3916Transport` 的寄存器层实现，以及 `IsoDepSession`（ISO-DEP / Type 4
目前整层未做，见 `REMAINING_WORK.md` R9 —— 它同样只依赖 `IRfidTransport`，可以先做）。

## 4. 验证口径

驱动落地时必须逐级说明，不要把前两级说成第三级：

| 级别 | 含义 | 本后端的现状 |
|---|---|---|
| `Model Verified` | 纯逻辑层经宿主套件断言 | 上电计划表与能力矩阵的结构已可断言；寄存器行为不能 |
| `Build Verified` | 真实工具链编译通过 | 当前 `nm-cyd-c5` `-fsyntax-only` 通过（不链接、不跑 `extra_scripts`） |
| `Hardware Verified` | 实机上电、读卡成功 | **未做，且在有实机与原理图之前无法做** |
