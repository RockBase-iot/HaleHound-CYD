## 1. 主机帧（Host ↔ PN532） — VERIFIED

```
前导            LEN   LCS   TFI   命令/数据        DCS   后导
00 00 FF        n     ~n+1  0xD4  ...             ...    00
```

- `LEN` **把 TFI 也算进去**，即 `LEN = 1 + 参数总长`。
- `LCS = ~LEN + 1`（二进制补码）。等效说法是「反码」，但对 `0x00` 两者一致，对其它值
  只有补码形式与硅片实测一致。
- `DCS` 覆盖 **TFI + 命令 + 参数**，是它们和的二进制补码 —— **不是反码**。多个移植版本
  在这里写成反码，只有在和恰好是 `0xFF` 时才碰巧相同。
- 应答方向字节 `0xD5`；**响应码 = 命令码 + 1**。

### 1.1 逐字节演算：`GetFirmwareVersion`

`LEN = 1 + 1 = 0x02`，`LCS = ~0x02 + 1 = 0xFE`；
`sum = 0xD4 + 0x02 = 0xD6`，`DCS = ~0xD6 + 1 = 0x2A`：

```
00 00 FF 02 FE D4 02 2A 00        ← 9 字节
```

`SamConfiguration(0x01, 0x14, 0x01)`：`LEN = 0x05`，`LCS = 0xFB`，
`sum = 0xD4+0x14+0x01+0x14+0x01 = 0xFE`，`DCS = 0x02`：

```
00 00 FF 05 FB D4 14 01 14 01 02 00
```

两条都作为硬编码字节串 pin 在 `test_pn532_protocol` 里。

### 1.2 真实应答样板（本轮实测对照）

PN532 1.6 对 `GetFirmwareVersion` 的应答，IC `0x32` / version `1` / revision `6` / support `7`：

```
00 00 FF 06 FA D5 03 32 01 06 07 E8 00
```

`LEN = 0x06 → LCS = 0xFA`；`sum(0xD5+0x03+0x32+0x01+0x06+0x07) = 0x18 → DCS = 0xE8`。

这条是**解码器唯一的独立锚点**：测试里的应答构造器和解码器如果共享同一个错误，硬编码
样板会让它露出来。同时它也 pin 了「64 字节固定缓冲读取时，后导之后的零填充必须被忽略」，
因为传输层就是这样读的（`kReplyReadSize = 64`）。

### 1.3 ACK 帧

```
00 00 FF 00 FF 00        ← 6 字节，不带方向字节
```

- 部分 I2C 读会连后导字节一起返回 7 字节，仍算 ACK。
- ACK 之后**还有别的字节**判为不是 ACK：那意味着一次读里回来了两帧，而主机只看了第一帧
  —— 这正是「上位机漏读」这类 bug 的表现。

## 2. 状态码 — VERIFIED

只列固件会据以动作的码；其余一律解成 `Unknown`，不编造原因（UM0701-02 Table 13）。

| 码 | 含义 | 映射到 `RfidStatus` | 理由 |
|---|---|---|---|
| `0x00` | 成功 | `Ok` | |
| `0x01` | 超时 | `Timeout` | |
| `0x02` / `0x03` | CRC / 奇偶错误 | `CrcError` | |
| `0x05` | 成帧错误 | `FrameError` | |
| `0x06` | 非正常冲突 | `Collision` | |
| `0x13` | DEP 数据格式不符 | `FrameError` | |
| **`0x14`** | **MIFARE 认证错误** | **`AuthFailed`** | **卡对密钥的判决** |
| `0x23` | UID 校验字节错误 | `FrameError` | 应答 SELECT 的是另一张卡 → 重新激活，不是卡判决 |
| `0x29` | 目标已被释放 | `NoTarget` | |
| `0x0A` | 射频场未开 | `IoError` | |
| `0x26` / `0x27` / `0x10` | 状态不允许 / 命令不接受 / 参数非法 | `Unsupported` | |
| 其它（含 `0x08`） | — | `IoError` | 未定义码 = 总线/主机问题 |

**`0x14` 与 `Unknown` 必须给出不同答案**，这是整条诚实上报链的全部立论基础：Adafruit 库的
`inDataExchange()` 把状态压成 `bool`，于是「卡拒绝了这把密钥」和「I2C 挂了」变成同一个
返回值；Key Check 在这个接口后面无法如实汇报，会**把死掉的总线报成一张在保护密钥的卡**。
`pn532StatusToRfid()` 是唯一知道这件事的地方，并有测试钉死两者不相等。

## 3. `InListPassiveTarget` 106 kbps type A 布局 — VERIFIED

（UM0701-02 §7.3.5.1）

| 偏移 | 字段 |
|---|---|
| 0 | `NbTg`（目标数） |
| 1 | `Tg`（目标号） |
| 2–3 | `SENS_RES` = ATQA，**低字节在前** |
| 4 | `SEL_RES` = SAK |
| 5 | `NFCIDLength` |
| 6… | `NFCID[]` |
| 之后 | `ATSLength` + `ATS[]`（仅 ISO14443-4 卡有） |

**ATQA 字节序**：`atqa = data[2] | (data[3] << 8)`。MIFARE Classic 1K 的 ATQA 是 `0x0004`，
线上即 `04 00`。

**UID 是线上顺序**（`uid[0]` 是先发的那个字节）。工具里打印的那个数码是前四字节**倒序**
读出的 —— 见 `MifareClassicModel::uid32()`。

**部分 ATS 不当作短 ATS**：`ATSLength` 声称 n 字节而实际不足 n 时，`atsLength` 保持 0。
截断的读 ≠ 一张 ATS 很短的卡；把前者当后者会让 DESFire 的协议版本静默错位。

**`NbTg` 判读**：`pn532PassiveTargetCount()` 对「不是 `InListPassiveTarget` 应答」的帧
返回 `0xFF`，而不是 0。这样调用方能区分「场上没卡」与「读卡器答了我看不懂的东西」——
两者在 UI 上应该是不同的状态。

**多于一张卡**（`NbTg != 1`）时解析失败：两张卡是操作员必须处理的冲突，不是解析器该替
他挑一张的场景。

## 4. MIFARE 认证帧附加 UID — PARTIALLY VERIFIED（刻意偏离数据手册）

规范形式（`Iso14443aFraming::buildAuthenticate`）为 8 字节：

```
0x60|0x61   block   key[6]
```

数据手册 UM0701-02 §7.3.9 描述的 `InDataExchange` 递送的就是这 8 字节。但**本板 RFID
代码一直以来使用的形式在末尾追加了 PICC UID**，成为 `10 + uidLength` 字节：

```
0x60|0x61   block   key[6]   UID[uidLength]
```

**证据等级：`PARTIALLY VERIFIED`。** 依据是本仓库历史代码 + 该形式在真实 PN532 硅片上
被验证过；本轮**没有**重做硬件复现。

处理方式（这是本项的重点）：

- 偏离被**关在 `Pn532Transport::transceive()` 里**，那是拥有该 quirk 的那一层。
- `Iso14443aFraming::buildAuthenticate()` 保持规范的 8 字节，因此**裸收发器**（预留的
  ST25R3916 通道）送出的仍是数据手册形式，不会被这个 quirk 污染。
- 只有 `txLength == 8 && tx[0] ∈ {0x60, 0x61}` 且已激活目标时才扩展，因此读块（`0x30`）
  等数据帧长度不变 —— 有测试分别钉死「8 字节认证帧变成 14」与「2 字节数据帧保持 4」。

## 5. ISO14443-A /-3 字节层 — VERIFIED

### 5.1 CRC_A（ISO/IEC 14443-3）

| 参数 | 值 |
|---|---|
| 多项式 | `0x1021`（x¹⁶+x¹²+x⁵+1） |
| 输入/输出反射 | 是 / 是 |
| 初值（目录形式） | `0xC6C6` |
| 初值（反射寄存器形式） | `0x6363` |
| 末异或 | `0x0000` |
| 校验值（对 `"123456789"`） | `0xBF05` |

**初值的两种写法是同一个 CRC**，只是在寄存器里的朝向不同。反射实现从 `0x6363` 起步
（`RfidTransport.cpp`），这与 libnfc 的 `CRC_A` 一致。写进注释是为了防止后来者「修正」
一个正确的常量。

线上按**小端**追加：`data[length] = CRC & 0xFF`，`data[length+1] = CRC >> 8`。

回归向量：`CRC_A(30 04) = 0xEE26`，故 NTAG READ page 4 的完整帧是 `30 04 26 EE`。

### 5.2 短帧

`REQA = 0x26`、`WUPA = 0x52`，**单字节、不带 CRC**。

### 5.3 级联与 Cascade Tag

| UID 长度 | 级联层数 | 命令码 |
|---|---|---|
| 4 | 1 | `0x93` |
| 7 | 2 | `0x93`, `0x95` |
| 10 | 3 | `0x93`, `0x95`, `0x97` |

每层起始 UID 偏移 = `(level-1) * 3`，每帧 4 个槽位：

- **非末层**：槽 0 = Cascade Tag `0x88`，槽 1–3 = `uid[offset..offset+2]`（三个 UID 字节）。
- **末层**：槽 0–3 = `uid[offset..offset+3]`（四个 UID 字节，无 CT）。

`NVB = 0x70`，随后是 BCC（4 字节异或）与 CRC_A，整帧 9 字节。

7 字节 UID `04 12 34 56 78 9A BC` 的逐字节演算：

```
L1: 93 70 88 04 12 34 AA
L2: 95 70 56 78 9A BC 08
```

> **实现时踩过的坑（已在 2026-10-15 修掉）**：初版在槽 0 写 CT 的同时，槽 1–3 仍按
> `uid[offset+1..offset+3]` 取值，于是 `uid[offset]` 被整字节丢掉。7 字节 UID 的 L1 会
> 发出 `88 12 34 56`（应为 `88 04 12 34`）—— 少一个 UID 字节且 BCC 全错，真机上表现为
> SELECT 永不匹配。测试同时钉住了 L1 的 `memcmp` 与 10 字节 UID 的 L1/L2/L3。

### 5.4 SAK 卡型映射（AN10833 Table 6）

| SAK | 卡型 |
|---|---|
| `0x00` | Ultralight / NTAG（**须同时满足 ATQA 低字节 = `0x44`**） |
| `0x08` | MIFARE Classic 1K |
| `0x09` | MIFARE Mini |
| `0x18` | MIFARE Classic 4K |
| `0x20` | ISO14443-4（DESFire / Plus SL3 / Type 4） |
| `0x28` / `0x38` | SmartMX 1K / 4K |
| `0x88` | Infineon Classic 1K |
| `0x10` / `0x11` | Plus SL1 2K / 4K |
| `0x01` | TNP3xxx |
| `0x04` | 不完整 UID —— 出现在激活完成之后说明激活没走完，**不猜** |

`0x00` 这行刻意粗糙：Ultralight、Ultralight C 与整个 NTAG21x 在这里无法区分，只有
`GET_VERSION` 能分开，所以分类器只给到「Ultralight / NTAG」不给容量。ATQA 低字节不是
`0x44` 时返回 `Unknown`，而不是硬认成 NTAG。

### 5.5 ATQA 的 UID 长度字段

UID 长度字段是 **b8/b7，即第一个 ATQA 字节的 bit 7/6**，不是 16 位值的 bit 15/14：

```
uidLength = (atqa >> 6) & 0x03      // 0→4, 1→7, 2→10
```

**反例就是 MIFARE Ultralight 的 `00 44`**：高位字节是 0，若按 16 位值读会把 7 字节 UID
读成 4 字节。这个例子是这一行的存在理由。

### 5.6 NTAG GET_VERSION 容量字节

`GET_VERSION = 0x60`，应答 8 字节，其中存储容量字节：

| 值 | 型号 |
|---|---|
| `0x0F` | NTAG213 |
| `0x11` | NTAG215 |
| `0x13` | NTAG216 |

（NXP NTAG21x 数据手册 Table 28）

### 5.7 MIFARE ACK / NAK

MIFARE 短帧应答是 **4 位**码：ACK = `1010`，NAK = `0000`。

**本层只比较低半字节**，因为 PN532 交回的是单字节、4 位码在低半字节。这是**约定**而非
宽容：高半字节与 4 位码无关，比对高半字节会把恰好高半字节为 `0xA` 的其它值误判为 ACK。
若将来 SPI 后端交回的码是高位对齐的（`0xA0`），**必须在传输层归一化**，而不是放宽这里
—— 测试里有一条 `0xA0` 必须判为「不是 ACK」的钉子。
